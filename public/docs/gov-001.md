## 1. Purpose and Scope

This framework establishes the regulatory requirements for standardizing multi-site neural data sharing. Neural data covers all modalities the framework's tooling classifies: structural MRI, functional MRI, MR angiography, perfusion (arterial spin labeling), computed tomography, positron emission tomography (PET), diffusion MRI, field maps, scalp EEG, and intracranial EEG. Structural MRI includes T1-weighted, T2-weighted, FLAIR, proton-density weighted, and T2*-weighted (including susceptibility-weighted) contrasts, each classified independently by the tool. The framework is the authoritative source from which all SOPs and tools are derived. No operational deliverable shall be finalized without traceability to specific requirements in this document.

**Scope:** All multi-site neural data shared across institutions, covering 14 scan types (T1w, T2w, FLAIR, PDw, T2starw, MR angiography, CT, PET, DWI, ASL, fMRI, field maps, scalp EEG, iEEG) organized into 9 BIDS modality folders (anat, ct, pet, dwi, perf, func, fmap, eeg, ieeg). The framework additionally covers scanner-computed derivative maps (ADC, FA, TRACEW, minimum-intensity projections), which are placed in a dedicated `derivatives/scanner/` folder separate from the raw acquisitions in `primary/`.

Session-based organization uses one of three structure presets, chosen at the start of the organization tool's workflow: **Single session** (no session level and no sessions table, for datasets with one visit per subject); **Implant sessions**, a fixed three-session preset (pre-implant, post-implant, post-surgery); or **Custom timepoints**, for longitudinal studies not organized around an implant procedure, where a site defines its own timepoints (see SOP-BIDS-001 Section 5.4 for the full specification). The framework defines how data must be structured, validated, and de-identified before sharing through cloud and on-premise standardized data infrastructure toward building a learning health system infrastructure. The choice of specific infrastructure (institutional cloud, on-premise archive, etc.) is left to each site. The framework applies to any site independently, with no requirement to coordinate through a central team. The framework is grounded in four regulatory pillars: FAIR Data Principles, ALCOA+ Data Integrity, HIPAA/PHI Protections, and the NIH Data Management and Sharing Policy (2023), supplemented by Quality Management System (QMS) practices.

**The organization tool.** The organization tool referenced throughout this framework is NeuroGate, distributed as a desktop application (macOS on Apple Silicon, Windows, and Linux) with a bundled command-line interface, both downloaded from the project's GitHub Releases page. The project website (https://epilepsy-gui.vercel.app) hosts this documentation and a browser version of the same tool. In both, all processing runs on the user's own computer and no patient data is uploaded by the tool; the browser version cannot export files over 500 MB. The tool organizes, checks, and de-identifies data and writes a BIDS-based dataset (Section 4) to a local folder; conversion from DICOM, defacing, and upload to a data infrastructure are performed by the site outside the tool. Where this framework states that the tool performs a step, the step is limited to what is described here and in SOP-BIDS-001 and SOP-GUI-001; every other requirement is a site responsibility.

## 2. Regulatory Requirements

### 2.1 FAIR Data Principles

The FAIR principles (Wilkinson et al., 2016) are operationalized as follows:

| Principle | Requirement | Implementation |
|---|---|---|
| Findable | Persistent IDs; rich standardized metadata | BIDS folder naming; data infrastructure metadata |
| Accessible | Standardized retrieval with authentication | Platform-level access controls; authenticated retrieval |
| Interoperable | Formal vocabularies; cross-dataset compatibility | BIDS v1.8+ naming conventions in the NeuroGate BIDS-based layout (Section 4); NIfTI and EDF/BDF formats (NWB or Persyst for iEEG, see Section 3); JSON sidecars |
| Reusable | Provenance; community standards for reuse | Acquisition params in JSON; participants.tsv; CHANGES file (site-authored when a recipient needs it; see Section 4) |

### 2.2 ALCOA+ Data Integrity

All data must meet ALCOA+ standards. Key requirements and verification methods:

| Principle | Requirement | Verification |
|---|---|---|
| Attributable | Each upload linked to identified contributor | Sharing platform upload logs |
| Legible | Standardized formats (NIfTI, EDF, JSON); BIDS naming; no ambiguous abbreviations | Organization tool validation step; manual review |
| Contemporaneous | Acquisition timestamps preserved in JSON sidecars (date-shifted per subject on export, preserving relative timing; see Section 2.3) | JSON sidecar audit |
| Original | Source DICOMs retained; BIDS files are verified copies with documented conversion | dcm2niix logs; checksums |
| Accurate | Dataset follows the NeuroGate structure defined in SOP-BIDS-001 and the organization tool's validation step passes with no errors; metadata matches acquisition parameters; scanner-computed derivatives are separated from raw acquisitions so downstream analysis does not treat computed maps as source data | Validation step results; `derivatives/scanner/` folder review |
| Complete | All sessions have required modalities; all JSON fields populated; participants.tsv complete | Completeness checklist |
| Consistent | Identical naming conventions and metadata definitions across all sites | Cross-site audit |
| Enduring | Long-term storage on the site's chosen data infrastructure; backup procedures; retention per NIH requirements | Storage verification |
| Available | 24/7 platform access; API retrieval; offline backup at the originating site | Access verification |

**Scope of the tool's checks.** The organization tool's validation step checks BIDS structure (session and subject assignment, unclassified or orphaned files, unmatched gradient tables), PHI patterns in file and folder names, in sidecar text, in the cells of exported electrode, channel, event and other tables, and in the free-text fields of NIfTI headers, required files per session under the Implant sessions preset only, cross-session consistency, dataset-level metadata entry, consistency between channel and electrode tables, Persyst file pairs and a supplied sessions.tsv (as warnings), and, for PET, the presence of the BIDS-required PET sidecar fields (as a warning). It does not check per-modality required JSON fields for any other modality, check image dimensions (the organization tool reads them from the NIfTI header during detection and warns in its mapping step when a file name contradicts them, but does not validate them), check iEEG recording duration, or check scanner or site consistency. Those verifications remain site responsibilities under this section.

### 2.3 HIPAA / PHI Protection

All 18 HIPAA identifiers must be removed before data leaves the originating institution. Neuroimaging-specific PHI risks and required actions:

| Data Element | PHI Risk | Required Action | Verification |
|---|---|---|---|
| DICOM headers | Patient name, DOB, MRN | Strip all identifiers during dcm2niix conversion (site step; the tool does not accept DICOM input and does not convert) | Post-conversion header audit |
| Scan JSON sidecars | Patient name/ID/DOB, institution, staff names, and device identifiers can survive DICOM-to-NIfTI conversion into the `.json` sidecar | Known identifying fields (patient name, ID, birth date, address, telephone, other IDs/names; institution name, address, department; referring, performing and requesting physician; operator; station name; device serial number) are replaced with "X" by the organization tool on export, at any depth in the sidecar (nested objects and arrays included). Other free-text fields are scanned for PHI patterns during validation but are not rewritten. A sidecar that is not a valid JSON object cannot be de-identified, so the tool reports it as a blocking validation error and does not export it | Post-export sidecar spot-check |
| File names | May contain patient names/MRNs | Replace with BIDS `sub-<ID>` (no PHI linkage); the organization tool renames every exported file to its BIDS name and flags PHI patterns in source file and folder names during validation | Naming convention review |
| Facial features | 3D reconstruction from any structural MRI (T1w, T2w, FLAIR, PDw, T2starw) | Apply defacing (pydeface/mri_deface) before import; the organization tool does not deface and requires a defacing attestation before export whenever any T1w, T2w, FLAIR, PDw, or T2starw image is present. PET is exempt from defacing | Visual inspection |
| Dates | Exact dates may identify individuals | Shifted by a random per-subject offset (not zeroed, to preserve relative timing); applied automatically by the organization tool on export to EDF/BDF header start dates, the date fields of scan JSON sidecars (at any depth), the Persyst `.lay` test date, and the `acq_time` column of `sessions.tsv`. Dates found in EDF+/BDF+ annotation text are replaced with X rather than shifted. The offset is deliberately not recorded anywhere, including the tool's audit log, so true dates cannot be recovered from the dataset or the site's tool records | JSON sidecar date audit |
| EEG/iEEG headers and annotations | Patient name in recording ID; identifying text typed into event annotations or comments | Replace with coded subject ID. Automated by the organization tool on export for EDF/BDF headers (patient and recording fields) and EDF+/BDF+ annotations, where identifying text (the patient's code, name and birth date, the recording's admin and technician codes, SSNs, MRNs, dates, phone numbers and email addresses) is replaced with X at the same length while event text, timestamps and signal data are kept. Persyst `.lay` files are also de-identified: patient fields other than sex, handedness and test time are removed, the test date is shifted, and comment text is redacted the same way as annotations. NWB files and the Persyst `.dat` file are exported without de-identification and must be de-identified by the site before import. The automated redaction is pattern-based and may miss free-text identifiers it does not recognize | Header and annotation review |
| Electrode, channel, and event tables | Free text or coordinates could carry identifying information | Review before import. The organization tool scans the cells of these and other exported tables for PHI patterns during validation (numeric cells and the two-capitalized-words name check are skipped), but it does not de-identify them: tables are exported unchanged, so a finding must be fixed in the source file | Table review |
| Metadata entry (age, sex, handedness) | Free-text or precise date fields could identify individuals | Demographics are optional. Age ranges only; coded IDs; no direct identifiers. The organization tool does not collect demographics; a site that includes them adds them to participants.tsv after export | participants.json data dictionary review (site-authored) |

**Subject ID key management:** The key linking coded IDs to real patient identifiers is stored only at the originating institution in a secure, access-controlled system. It is never uploaded to any data infrastructure or shared externally.

**Organization tool audit log:** Every export writes two audit logs. The full audit log records original file and folder names (in user corrections and subject names) and the study name, which can identify patients. It must be kept in the originating site's records under the same controls as the subject ID key, and is never shared with or uploaded alongside the dataset. The shareable copy replaces each original file name and path with its exported BIDS path (or `file-N` if the file was not exported), each subject group with its assigned `sub-` ID (or `subject-N`), and the operator with "site"; otherwise it matches the full log. Only the shareable copy may accompany a dataset.

### 2.4 NIH Data Management and Sharing Policy (2023)

This framework ensures compliance with the NIH DMSP requirements: data types/formats specified (Section 3), metadata standards identified (Section 4), preservation on the site's chosen long-term data infrastructure, sharing timeline aligned with publication/grant end, access controls via platform permissions and data use agreements, and compliance monitoring (Section 6).

### 2.5 Quality Management System Practices

- **Version Control:** Major.minor format. Major for structural changes; minor for edits.
- **Document Numbering:** Unique IDs (GOV-001, SOP-BIDS-001, SOP-GUI-001).
- **Change Tracking:** All changes logged in each document's Revision History table with version, date, author, and summary.
- **Review/Approval:** Governance framework changes require advisor review.

## 3. Data Standards by Modality

All standards follow BIDS v1.8+ naming conventions within the NeuroGate BIDS-based structure (Section 4) and are supplemented by FAIR, ALCOA+, and HIPAA requirements. Each modality requires placement in the structure defined in SOP-BIDS-001, a pass of the organization tool's validation step with no errors, complete JSON sidecars, and de-identification before upload. The organization tool does not verify the JSON fields listed below, with the exception of PET, for which it warns when the sidecar is missing or lacks a field required by SOP-BIDS-001; completeness of the other modalities' sidecars is verified by the site.

The table below shows session assignments under the Implant sessions preset. A dataset using the Custom timepoints preset instead uses site-defined session labels with no fixed per-timepoint modality assignment, and a Single session dataset has no session level; see SOP-BIDS-001 Section 8 for the Custom timepoints requirements. All other requirements in this table (formats, JSON metadata, de-identification) apply under every preset.

| Modality | Session(s) | Format | Naming Example | Key Metadata (JSON) | De-ID Notes |
|---|---|---|---|---|---|
| T1w | pre-implant, post-surgery | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_T1w.nii.gz` | Manufacturer, MagneticFieldStrength, RepetitionTime, EchoTime, FlipAngle, SliceThickness | DICOM strip + facial defacing required |
| T2w | pre-implant, post-surgery | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_T2w.nii.gz` | Manufacturer, MagneticFieldStrength, RepetitionTime, EchoTime, FlipAngle, SliceThickness | DICOM strip + facial defacing required |
| FLAIR | pre-implant, post-surgery | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_FLAIR.nii.gz` | Manufacturer, MagneticFieldStrength, RepetitionTime, EchoTime, FlipAngle, SliceThickness, InversionTime | DICOM strip + facial defacing required |
| PDw | pre-implant | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_PDw.nii.gz` | Manufacturer, MagneticFieldStrength, RepetitionTime, EchoTime, SliceThickness | DICOM strip + facial defacing required |
| T2starw | pre-implant | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_T2starw.nii.gz` | Manufacturer, MagneticFieldStrength, RepetitionTime, EchoTime, FlipAngle | DICOM strip + facial defacing required |
| CT | post-implant | NIfTI (.nii.gz) | `sub-XX_ses-postimplant_ct.nii.gz` | Manufacturer, AcquisitionVoltage, SliceThickness, ConvolutionKernel | DICOM strip; defacing not required per current standard practice, though sites may apply it as an additional precaution |
| PET | pre-implant | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_trc-FDG_pet.nii.gz` | BIDS PET metadata fields required by SOP-BIDS-001: Manufacturer, ManufacturersModelName, Units, TracerName, TracerRadionuclide, InjectedRadioactivity, InjectedRadioactivityUnits, InjectedMass, InjectedMassUnits, SpecificRadioactivity, SpecificRadioactivityUnits, ModeOfAdministration, TimeZero, ScanStart, InjectionStart, FrameTimesStart, FrameDuration, AcquisitionMode, ImageDecayCorrected, ImageDecayCorrectionTime, ReconMethodName, ReconMethodParameterLabels, ReconFilterType, AttenuationCorrection (InjectedMass and SpecificRadioactivity and their units may be "n/a" but must be present) | DICOM strip; exempt from defacing (not covered by the tool's defacing attestation) |
| EEG (scalp) | pre-implant | EDF/BDF | `sub-XX_ses-preimplant_task-monitor_eeg.edf` | SamplingFrequency, EEGReference, PowerLineFrequency + electrodes.tsv, channels.tsv | Remove patient name from EDF/BDF header and identifying text from EDF+/BDF+ annotations |
| iEEG | post-implant | EDF/BDF, NWB, or Persyst (.dat + .lay) | `sub-XX_ses-postimplant_task-monitor_ieeg.edf` | SamplingFrequency, iEEGReference, ElectrodeManufacturer, iEEGPlacementScheme + electrodes.tsv, channels.tsv | Remove patient IDs; coordinates must not encode identifying info. The tool de-identifies EDF/BDF headers and annotations and Persyst `.lay` files; NWB files and the Persyst `.dat` file must be de-identified by the site |
| DWI | pre-implant | NIfTI + .bval + .bvec | `sub-XX_ses-preimplant_dwi.nii.gz` | Manufacturer, MagneticFieldStrength, RepetitionTime, EchoTime, PhaseEncodingDirection | DICOM strip; defacing not required |
| MR Angiography (TOF) | pre-implant | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_angio.nii.gz` | Manufacturer, MagneticFieldStrength, RepetitionTime, EchoTime, FlipAngle | DICOM strip; defacing recommended |
| fMRI (BOLD) | pre-implant | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_task-rest_bold.nii.gz` | Manufacturer, MagneticFieldStrength, RepetitionTime, EchoTime, TaskName, SliceTiming | DICOM strip; defacing recommended |
| Perfusion (ASL) | pre-implant | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_asl.nii.gz` | Manufacturer, MagneticFieldStrength, RepetitionTime, EchoTime, ArterialSpinLabelingType, PostLabelingDelay | DICOM strip; defacing recommended |
| Field Map | pre-implant | NIfTI (.nii.gz) | `sub-XX_ses-preimplant_magnitude1.nii.gz`, `..._magnitude2.nii.gz`, `..._phasediff.nii.gz` | Manufacturer, MagneticFieldStrength, EchoTime1, EchoTime2, IntendedFor | DICOM strip; defacing not required |

**Task labels.** The organization tool names functional MRI runs `task-rest` and scalp EEG and iEEG recordings `task-monitor` unless the user sets another task label in its mapping step; a functional run's sidecar `TaskName` is set to match, and channels and events tables follow their recording's task. It places electrodes, channels, and events tables beside their recording: in `eeg/` for scalp EEG and in `ieeg/` for iEEG, matching each table to an EEG or iEEG recording in the same source folder first, then in the same subject and session; a table with no match, or where both kinds of recording are present, is placed in `ieeg/`. It fills the field-map `IntendedFor` field with every echo-planar image exported in the same session.

**Localizer and scout scans:** Localizer and scout acquisitions are recognized by the organization tool but are excluded from the shared dataset. They are acquisition aids used to plan the diagnostic scans, not analyzable data, and are not part of a BIDS dataset.

**PET attenuation-correction images.** The CT (or MR-derived mu-map) that a PET/CT or PET/MR scanner acquires only to correct the PET image for attenuation is recognized by the organization tool and is not exported. A user can reclassify such a file as CT in the tool's mapping step if it is a diagnostic scan. PET images are named with the BIDS `trc-<tracer>` entity, taken from the sidecar `TracerName` or the file name, and, when a session contains both attenuation-corrected and uncorrected images, a `rec-` entity that distinguishes them. PET in ECAT format and PET blood data are not accepted by the tool; ECAT files must be converted to NIfTI before import.

**File compression:** The required imaging format is gzip-compressed NIfTI (`.nii.gz`). Uncompressed `.nii` files submitted to the organization tool are automatically compressed to `.nii.gz` on export, so this requirement is enforced by the tool without a separate manual compression step.

**Repeated acquisitions.** When a subject and session contains more than one acquisition of the same modality (for example, two T2w scans in a single visit), each acquisition is given a BIDS `run-` entity (`run-1`, `run-2`, and so on) so that every file has a unique name. The organization tool assigns these entities automatically. A scan's companion files (its JSON sidecar, and the `.bval` and `.bvec` files for diffusion) share the same run number as the imaging file.

**Magnitude and phase pairs.** When a susceptibility-weighted or T2*-weighted acquisition produces both a magnitude and a phase image from a single scan, both files share the same run number and are distinguished by the BIDS `part-mag` and `part-phase` entities. Sharing the run number indicates the two files come from one acquisition rather than two separate acquisitions of the same modality, as required by BIDS to represent complex-valued imaging correctly.

**Motion-corrected reconstructions.** When a scanner produces both a raw functional run and a motion-corrected reconstruction of the same acquisition (Siemens `MoCoSeries`), both files share the run number and the reconstructed version is marked with the BIDS `rec-moco` entity. This distinguishes an on-scanner reconstruction from a separate acquisition.

**Single-band reference volumes.** Multiband diffusion and functional sequences acquire a single-band reference volume alongside the main acquisition. The reference is exported with the BIDS `sbref` suffix and the same run number as the main acquisition. It is used by downstream analysis pipelines for distortion correction and registration.

**Field maps.** A gradient-echo field map produces two magnitude images (at two echo times) and one phase-difference image. These are named with the standard BIDS field-map suffixes (`magnitude1`, `magnitude2`, `phasediff`, or `phase1` and `phase2` when two phase images are present) rather than a single shared suffix, so each image is individually addressable per the BIDS specification. The `EchoTime1` and `EchoTime2` values required in the JSON sidecar accompany the `phasediff` image. When a session contains multiple gradient-echo field-map series (for example, one for diffusion and one for functional MRI), each series receives its own `run-` number with a complete `magnitude1`, `magnitude2`, and `phasediff` triple. The organization tool names field maps only under this magnitude/phase scheme; it does not produce the BIDS `epi` suffix used for reverse-polarity EPI field maps.

**Diffusion gradient tables.** Every raw diffusion image requires an accompanying `.bval` and `.bvec` gradient table. The organization tool pairs a gradient table with its image by shared base name and, when a site named them independently, by matching the b-value and phase-encoding direction of the acquisition. A gradient table that cannot be paired this way is flagged with a warning and held out of the export rather than guessed, because attaching a wrong gradient table to a diffusion image produces plausible-looking tractography output from incorrect gradient directions.

**Scanner-computed derivative maps.** Diffusion sequences frequently produce derivative maps computed on the scanner console alongside the raw acquisition: apparent diffusion coefficient (ADC), fractional anisotropy (FA), and trace-weighted (TRACEW) maps. Susceptibility-weighted sequences may produce minimum-intensity projections. Under BIDS conventions these belong under `derivatives/`, and they must not be placed in the raw acquisition folders because downstream analysis pipelines would misinterpret computed maps as source data. The organization tool routes them to a dedicated `derivatives/scanner/` folder using the BIDS `desc-<label>` entity to identify each derivative type (for example `desc-ADC`, `desc-FA`, `desc-TRACEW`, `desc-mIP`). See Section 4 for the folder structure.

## 4. Metadata Completeness Requirements

Dataset-level files (per FAIR and ALCOA+):

| File | Contents | Source |
|---|---|---|
| dataset_description.json | Name, BIDSVersion, DatasetType, Authors, GeneratedBy | Generated by the organization tool from the study name and authors entered in its metadata step |
| participants.tsv | `participant_id` for every subject, plus any demographic fields (age, sex, handedness) the site includes | The organization tool generates the file with the `participant_id` column only, listing each subject that has exported data. It does not collect demographics; a site that includes them adds them after export, following Section 2.3. PHI is never entered into the tool |
| participants.json | Data dictionary documenting each participants.tsv field's meaning and coding | Written by the site if a recipient needs it; not generated by the tool |
| README | Dataset overview, contact, collection protocols, known issues | Written by the site if a recipient needs it; not generated by the tool |
| CHANGES | Version history of dataset changes per BIDS format | Written by the site if a recipient needs it; not generated by the tool |

Each acquisition must include a JSON sidecar with fields per Section 3. EEG and iEEG require electrodes.tsv and channels.tsv with no empty required fields. The organization tool requires electrodes.tsv and channels.tsv to be present in the post-implant session under the Implant sessions preset and warns when an iEEG session has no electrodes.tsv; it does not check that their required fields are filled, and scans their cells for PHI patterns only (Section 2.3).

**Session table.** Under the Implant sessions and Custom timepoints presets the organization tool writes a `sub-<ID>_sessions.tsv` per subject with `session_id` and `acq_time` (date-shifted, ISO 8601), listing only the sessions that have exported data. A Single session dataset has no session table.

**Dataset folder structure.** Every dataset uses a two-folder top-level layout that separates raw acquisitions from scanner-computed derivative maps. The `primary/` folder holds the raw, acquired data organized by subject and session. The `derivatives/scanner/` folder holds scanner-computed maps produced by the acquisition console, mirroring the `primary/` structure. The organization tool populates `primary/` on every export and creates `derivatives/scanner/` only when scanner-computed maps are present; it does not write a separate `dataset_description.json` inside `derivatives/scanner/`. Site-specific analysis pipelines may add additional subfolders under `derivatives/` outside the tool. See SOP-BIDS-001 Sections 5 and 9 for the full specification.

**NeuroGate structure and the BIDS specification.** The export layout (`bids_output/` containing `dataset_description.json`, `participants.tsv`, `primary/sub-*/...`, and `derivatives/scanner/...`) is NeuroGate's own BIDS-based structure, designed deliberately by the project. File names, entities, datatype folders, and sidecars follow BIDS conventions, but the root layout (subjects under `primary/`, scanner derivatives under `derivatives/scanner/`) intentionally differs from the official BIDS specification. The official BIDS validator expects subjects at the dataset root and so does not apply to the NeuroGate layout as a whole; conformance under this framework means the dataset follows the structure defined in SOP-BIDS-001 and passes the organization tool's own validation step (the Validate step in the desktop application, or the command-line interface's validation) with no errors.

## 5. Audit Traceability

Every dataset must have a documented provenance chain: original acquisition (DICOM), then conversion (dcm2niix), then de-identification, then BIDS organization, then validation, then upload. Each step must be timestamped and attributable. Required audit records:

| Record | Contents | Location |
|---|---|---|
| Conversion Log | dcm2niix command, version, parameters, file counts | Local site records |
| Defacing Log | Tool, version, files processed, QA result | Local site records |
| Validation Record | Outcome of the organization tool's validation step (no errors), and the site's disposition of any warnings and dismissed issues | Local site records (recorded by the site; the tool logs only that validation passed) |
| Organization Tool Audit Log | Structure selected and any later structure change, files scanned, detection as aggregate counts (per-file detection reasons are visible in the Mapping step but not logged), every user correction to subject, session, modality, and task (old and new values; bulk edits as a count), metadata entry, defacing attestation (given, removed, or cleared because the structural MRI files changed), each dismissed validation issue, validation passed, export completed, and a de-identification summary (fields replaced or shifted, annotation and `.lay` redaction counts; no date-shift values or redacted text) | Full log: local site records only; written by the tool next to the exported `bids_output/` folder as `audit_log_<timestamp>.json` (`audit_log.json` from the command-line interface) and not shared with the dataset. Shareable copy: written alongside it as `audit_log_<timestamp>_shareable.json` (`audit_log_shareable.json` from the command-line interface), with original names replaced by BIDS paths and `sub-` IDs; this is the copy that may be sent with the dataset (see Section 2.3) |
| Upload Log | Sharing platform upload log: files, timestamps, status | Sharing platform (typically automatic) |
| PHI Clearance | De-identification completion recorded per the pre-upload checklist | Local site + project archive |

The organization tool's audit log attributes each entry to "user" or "system" in the desktop application and to the operating-system username in the command-line interface; the tool has no user accounts. Sites record the identity of the operator who ran each session in their own records. The log records detection as aggregate counts only; per-file detection reasons are visible in the Mapping step but are not logged. It does not record dismissed validation issues or errors.

## 6. Compliance Verification

### 6.1 Pre-Upload Checklist (Per Subject)

The following must be verified before each upload:

- Dataset follows the NeuroGate structure defined in SOP-BIDS-001, and the organization tool's validation step (Validate step or CLI validation) reports no errors (warnings acceptable if documented)
- All required metadata files present and complete (JSON sidecars, participants.tsv, electrodes/channels.tsv), plus the site-authored participants.json, README, and CHANGES where a recipient needs them
- De-identification completed: DICOM headers stripped, defacing applied to all structural MRI modalities, file names coded, dates removed or shifted, EDF/BDF headers and annotations cleaned, Persyst `.lay` files cleaned by the tool and `.dat` files checked by the site, NWB files de-identified by the site, electrode/channel/event tables reviewed for PHI (including any findings from the tool's table scan)
- PHI Clearance confirmed
- File sizes consistent with expected data volumes
- Full organization tool audit log retained in local site records and excluded from the shared dataset; if an audit record is sent with the dataset, it is the shareable copy only

### 6.2 Periodic Audits

Quarterly audits shall review a sample of uploaded datasets. Non-conformances are classified as Critical (data integrity/PHI risk), Major (incomplete metadata/missing records), or Minor (formatting/documentation gaps). Corrective actions are tracked to closure.
